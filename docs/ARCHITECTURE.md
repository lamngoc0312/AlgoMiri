# AlgoMiri — Initial Architecture

## Strategy
Start with a modular frontend-only vertical slice, then add FastAPI and persistence behind interfaces. Avoid premature microservices and do not force a node-editor renderer onto every visual: SVG/React is appropriate for arrays; React Flow is useful for graphs, trees and conceptual solution maps.

## Shared domain concepts (TypeScript first; later mirrored in Python/Pydantic)
### ProblemSpec
`id`, `provider`, `providerId?`, `title`, `statement`, `constraints`, `examples`, `inputSchema`, `outputSchema`, `supportedStrategies[]`, `supportedVisualization`.

### SolutionStrategy
`id`, `problemId`, `name`, `intuition`, `timeComplexity`, `spaceComplexity`, `techniques[]`, `learningGraphId?`.

### SolutionGraph (conceptual, may be a DAG)
`nodes[]` (id, title, learningGoal, skills[], rationale), `edges[]` (source, target, reason), `strategyId`. This models the learner's reasoning; do not assume it equals the runtime execution graph.

### ExecutionStep (deterministic)
`id`, `stepIndex`, `action`, `line?`, `variables`, `visualState`, `highlightedIndices[]`, `explanation`, `isTerminal?`.
A trace is a list of immutable steps generated by a pure function of (strategy, validated input). React renders snapshots, it never invents algorithm transitions.

### LearningAttempt (future)
`userId`, `problemId`, `strategyId`, `startedAt`, `completedAt?`, `result`, `hintsUsed`, `predictionAccuracy?`, `selfRatedConfidence?`.

### SkillEvidence (future)
`skillId`, `attemptId`, `source`, `independenceLevel`, `success`, `recordedAt`. "Viewed visualization" alone must not count as mastery.

## MVP tracing architecture
1. UI validates input (array of finite safe integers, target integer, max length for smooth animation).
2. Pure brute-force and hash-map functions compute ordered `ExecutionStep[]` and result.
3. Timeline state manages selected strategy, current step, playback speed. Switching strategies resets position.
4. Canvas renders the selected `visualState` with clear labels / legend; text panel uses matching `explanation`.
5. Unit tests compare results with a simple correctness oracle and assert no inconsistent step indices.

## Multi-Problem Architecture (Sprint 4–5)
- **`ProblemModule<TInput, TVisual>` (`web/src/domain/core/types.ts`)**: Encapsulates a problem's `ProblemSpec`, strategies (variable count per problem), default input & presets, deterministic `generateTrace()`, conceptual `SolutionGraph`s, `ProblemLesson` (stages, 3-level hints, progressive pseudocode), and dynamic `generatePrediction()`.
- **Discriminated Union `AnyVisualState`**: Uses `kind: 'array-hash' | 'stack'` rather than a single optional-field god object, allowing dedicated renderers (`VisualCanvas` for arrays/hash maps, `StackVisualCanvas` for vertical LIFO stacks) while sharing `useTracePlayback`, `PlaybackControls`, `WalkthroughPane`, `GuidedStagePanel`, `PredictNextStepCard`, and `SessionSummaryCard`.
- **`ProblemRegistry` (`web/src/domain/problems/registry.ts`)**: Central lookup powering `/problems` and `/studio/:problemId` (with `/studio` redirecting to `/studio/two-sum`). Keying the Studio workspace by `problemModule.id` guarantees clean playback and learning state resets when switching problems.

## Conceptual SolutionGraph & Future Algorithm Composition (Sprint 5+)
- **Strict Separation from Runtime Execution:** A `SolutionGraph` is a conceptual DAG of reasoning subgoals (`input-model`, `invariant`, `operation`, `decision`, `technique`, `termination`) validated by `validateSolutionGraph()` (`web/src/domain/solutions/graphValidator.ts`) for duplicate IDs, missing references, self-dependencies, and cycles. Loops are NEVER forced into DAG cycles; instead, each conceptual node declares `mappedActions[]` linking it to verified `ExecutionStep.action` snapshots for synchronized **Macro View** (Solution Map) and **Micro View** (Execution Trace) learning.
- **Preparing for Multi-Technique Composition (e.g., Binary Search on Answer + Greedy Feasibility Check):**
  - Each node supports `category: 'technique'`, `techniques: string[]`, and an optional `ioContract: { inputs: string[]; outputs: string[] }` describing the conceptual data contract between techniques.
  - For a future problem like *Allocate Minimum Pages* or *Koko Eating Bananas*:
    1. `monotonic-range` (`input-model`): outputs `[low, high]` candidate answer bounds.
    2. `binary-search-driver` (`technique`, `techniques: ['Binary Search on Answer']`): consumes `[low, high]`, outputs `candidate mid` to the feasibility check.
    3. `greedy-feasibility` (`technique`, `techniques: ['Greedy']`): consumes `(items[], candidate mid)`, outputs `feasible: boolean` via a linear greedy pass.
    4. `narrow-bounds` (`decision`): depends on BOTH `binary-search-driver` and `greedy-feasibility` (merging their branches), narrowing `[low, high]` until convergence.
  - This models how two distinct algorithmic techniques compose conceptually via explicit data contracts while keeping deterministic execution trace generation completely separate.

## Future AI boundary
LLM only proposes `ProblemAnalysis` and strategies in structured JSON (validated at API boundary). Candidate strategy must be checked against supported engine and tests before a "verified visualization" is offered. Other problems get explicitly marked conceptual/explanatory mode. Never auto-execute generated source in the web server.

## Security and legality
No secret values in client bundle or repo. No user-password request for coding sites. No automatic scraping of LeetCode statements. Respect provider metadata and rate limits. Treat pasted statements as user-owned private input; minimize logging and storage.
